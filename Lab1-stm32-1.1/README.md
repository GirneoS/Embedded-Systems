# Магнитометр SDK-1.1M: STM32 + клиент для ПК

Проект для STM32F427VIT6 в STM32CubeIDE. Прошивка постоянно выводит компоненты магнитного поля X, Y, Z в мкТл и после калибровки — стрелку направления поля на OLED. Python-клиент показывает те же данные, управляет калибровкой, задаёт три масштабных коэффициента от 0 до 200% и автоматически записывает весь обмен UART в журнал.

## Запуск прошивки

1. В STM32CubeIDE обновить проект: **Refresh / F5**. Если IDE предлагает перечитать изменённый `.cproject`, согласиться.
2. Выполнить **Project → Clean**, затем **Build Project**. Новые файлы из `Core/Src` попадут в сборку автоматически.
3. Загрузить программу через существующую конфигурацию отладки стенда.

В `main.c` вызываются `Compass_Init()` и `Compass_Process()`. Их вызовы расположены в блоках `USER CODE`, поэтому сохраняются при генерации кода CubeMX. UART работает на 38400 бод, системная частота — 90 МГц. I2C1 выведен на PB8 (SCL) / PB9 (SDA), как требуется для проверенного стенда; эта распиновка записана и в `.ioc`, и в `Core/Src/i2c.c`.

Сохранённая конфигурация Debug использует `SDK1_1_M FTDBG.cfg` и `SDK11M_FT.cfg`. Для OpenOCD 0.11 из CubeIDE 2022 в этих файлах явно описаны оба TAP STM32F427: ARM debug с длиной IR 4 и ST boundary scan с длиной IR 5. Установлены JTAG 1000 кГц и подключение под аппаратным сбросом. Это устраняет автоматический неопределённый `auto0.tap` из старого target-скрипта. Частоту для этого скрипта задаёт `CLOCK_FREQ` в файле стенда.

После исправления на реальном стенде проверены подключение GDB через `target extended-remote localhost:3333`, аппаратная точка останова в `main()`, отключение с продолжением исполнения и запись ELF с `Verified OK`. Идентификатор MCU прочитан как `0x20016419`, Flash — 2048 КиБ. Область первых 64 КиБ предыдущей программы, покрывающая все сектора, затронутые загрузкой текущей сборки, сохранена в `.hardware-backups/flash-before-compass-20261112-112435.bin`.

При ошибке `Failed to enable the FPB`, множественных `DAP transaction stalled (WAIT)` и сообщении о `auto0.tap` использовать именно обновлённый файл стенда, затем завершить старый сеанс Debug и запустить его снова. Первоначальная распиновка PB6/PB7 в проекте не была подключена к устройствам I²C этого стенда; после переноса на PB8/PB9 аппаратно подтверждены LSM9DS1 на `0x1C`, работа OLED и непрерывная телеметрия. В новой версии без калибровки флаги равны `9`, после калибровки при достоверном угле — `27`.

Сборка с калибровкой загружена и проверена OpenOCD (`Verified OK`). На подключённом стенде UID `003B00373039510938303439` проверены PING протокола 2, свежие значения LSM9DS1, доступность OLED и реальный сбор/отмена калибровки. Журнал: `logs/hardware-calibration-check-20261112-122400.jsonl`. Предыдущие первые 64 КиБ Flash сохранены в `.hardware-backups/flash-before-calibration-20261112-122246.bin`. Физические повороты и привязку к северу выполняет пользователь по мастеру; программная проверка не заменяет их.

Предыдущая программа гирлянды остаётся в `Core/Src/lab3.c`, но исключена из Debug и Release в `.cproject`. Одновременно включать её в сборку нельзя: обе программы определяют UART callbacks.

Можно проверить сборку без запуска IDE:

```sh
python3 tools/build_firmware.py
```

Скрипт ищет ARM GCC в `PATH` и в установленной на macOS STM32CubeIDE. При необходимости путь задаётся параметром `--gcc`. Результат: `build-compass/compass.elf` и `build-compass/compass.hex`. Каталог `Debug` скрипт не использует; IDE создаёт свои файлы сборки отдельно.

## Запуск клиента

Нужен Python 3.9 или новее с работающим Tkinter. Проверка Tkinter: `python3 -m tkinter` должна открыть тестовое окно. Если системный Python на macOS не открывает окна Tk, использовать сборку Python с поддержкой Tk, например с [python.org](https://www.python.org/downloads/macos/).

Команды выполняются из корня проекта.

macOS на Apple Silicon с Homebrew:

```sh
brew install python-tk@3.14
/opt/homebrew/bin/python3.14 -m venv .venv-gui
.venv-gui/bin/python -m pip install -r client/requirements.txt
.venv-gui/bin/python -m serial.tools.list_ports
.venv-gui/bin/python client/main.py /dev/cu.usbserial-101
```

Явный путь к интерпретатору важен: команда `python3` может по-прежнему запускать Apple Python 3.9 из Command Line Tools с Tcl/Tk 8.5. На macOS 26 эта связка может завершаться с сообщением `macOS 26 (2602) or later required, have instead 16 (1602)` ещё до открытия окна. Клиент проверяет старый Tk до инициализации GUI и выводит понятную ошибку. Обновлять macOS для устранения этой ошибки не требуется. [Python.org о системном Tcl/Tk](https://www.python.org/download/mac/tcltk/), [пакет Homebrew python-tk@3.14](https://formulae.brew.sh/formula/python-tk@3.14).

У Homebrew Python на macOS 26.2 также возможна отдельная ошибка `pyexpat: Symbol not found: _XML_SetAllocTrackerActivationThreshold`, которая мешает созданию виртуального окружения. Причина — бинарный пакет использует более новую Expat, чем системная библиотека этой версии macOS; см. [обсуждение Homebrew](https://github.com/orgs/Homebrew/discussions/6798). На этом Mac для Python 3.14.10 проблема уже исправлена: установлен Homebrew `expat` 2.10.0, модуль `pyexpat` привязан к `/opt/homebrew/opt/expat/lib/libexpat.1.dylib` и заново подписан локальной подписью. Исходный модуль сохранён в `.venv-gui/homebrew-backup/pyexpat.cpython-314-darwin.so.original`. Обновление или переустановка Homebrew Python может заменить этот модуль. Для новой установки на другой машине альтернативой является официальный macOS-установщик Python с python.org.

Окружение `.venv-gui` создаётся новым Python и не изменяет старое `.venv`. Виртуальное окружение, созданное Apple Python, само по себе не обновляет Tcl/Tk. На Intel Mac путь Homebrew обычно начинается с `/usr/local`; используйте соответствующий установленный `python3.14`. Имя порта сверять со списком устройств: на проверенном стенде канал UART был `/dev/cu.usbserial-101`.

Linux с установленным Tkinter:

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r client/requirements.txt
python -m serial.tools.list_ports
python client/main.py /dev/cu.usbserial-XXXXXXXX
```

Windows PowerShell:

```powershell
py -m venv .venv
.venv\Scripts\python.exe -m pip install -r client/requirements.txt
.venv\Scripts\python.exe -m serial.tools.list_ports
.venv\Scripts\python.exe client/main.py COM5
```

Имя порта — позиционный аргумент запуска. UART: **38400 бод, 8 бит, без чётности, 1 стоп-бит, без управления потоком**. Порт должен быть свободен от других терминальных программ.

После открытия порта первая отправляемая команда — `PING`. После `PONG` клиент запрашивает текущие коэффициенты и статус калибровки; повторное подключение не сбрасывает их. Если в ПК сохранён профиль именно этого микроконтроллера, он автоматически восстанавливается. При первом подключении открыть вкладку **«Калибровка»** и выполнить шаги ниже. Клиент поддерживает старую прошивку протокола 1 для просмотра/масштабирования, но для калибровки необходимо прошить новую версию.

На вкладке **«Измерения»** ввести коэффициенты или переместить ползунки и нажать **«Применить X, Y, Z»**. Поля **«На стенде»** показывают подтверждённые коэффициенты. Кнопка **«Ввести 100%»** только заполняет поля; для отправки нажать **«Применить»**.

Просмотр интерфейса без стенда и без pyserial (использовать Python с рабочим Tkinter, на macOS — `.venv-gui/bin/python`):

```sh
python3 client/main.py --demo
```

Режим явно обозначен как демонстрационный. Обмен в нём проходит через те же кодек, поток связи и журнал, но данные создаёт эмулятор.

Журнал создаётся автоматически в `logs/uart-ДАТА-ВРЕМЯ.jsonl`. Другой путь задаётся через `--log путь.jsonl`; существующий файл дополняется. Каждая запись содержит время ПК с часовым поясом. Записи `bytes` содержат направление `TX`/`RX`, точные байты в `hex` и читаемое представление `text`. Записываются также неполные, повреждённые и неизвестные входные данные. Записи `message` содержат разобранные сообщения и собственную метку времени. Ошибки CRC фиксируются отдельно. Данные сбрасываются в файл после каждой записи. Если журнал открыть невозможно, клиент не начинает обмен.

## Аппаратура и расписание

| Узел | Настройка |
| --- | --- |
| Микроконтроллер | STM32F427VIT6, системная частота 90 МГц |
| Связь с ПК | USART6, PC6 TX / PC7 RX, 38400 8N1 |
| I²C | I2C1, PB8 SCL / PB9 SDA, 100 кГц |
| Магнитометр | Автоопределение LSM9DS0 или LSM9DS1 по `WHO_AM_I` |
| OLED | SSD1306, 128×64, 7-битный адрес `0x3C` |
| Сброс OLED | PCA9538, 7-битный адрес `0x70`, выход P0 |

Адреса в таблице — 7-битные. На границе STM32 HAL они сдвигаются влево на один бит: `0x3C → 0x78`, `0x70 → 0xE0`. Аппаратный сброс OLED через P0 взят из [руководства SDK-1.1M, раздел 1.8, стр. 30](https://books.ifmo.ru/file/pdf/3031.pdf). Другие биты расширителя сохраняются.

У LSM9DS0 проверяются адреса `0x1D` и `0x1E`, идентификатор `0x49`; используются высокое разрешение, 50 Гц и диапазон ±12 гаусс. Дополнительно поддержан LSM9DS1: `0x1C`/`0x1E`, идентификатор `0x3D`, 40 Гц, диапазон ±16 гаусс. Датчик определяется по идентификатору до записи регистров. Чувствительности 48 и 58 нТл/отсчёт взяты из таблиц 3 [LSM9DS0](https://www.st.com/resource/en/datasheet/lsm9ds0.pdf) и [LSM9DS1](https://www.st.com/resource/en/datasheet/lsm9ds1.pdf).

UART принимается по прерыванию в кольцевой буфер на 512 байт. В ISR выполняются только сохранение байта и повторный запуск приёма. Разбор команд, ответы, расчёты и I²C выполняются в основном цикле. Передача UART — по опросу с конечным тайм-аутом.

Все транзакции I²C синхронные, из одного контекста; таймерные прерывания для них не используются. Магнитометр опрашивается примерно каждые 40 мс, а кадр OLED и соответствующая телеметрия формируются каждые 200 мс. Буфер экрана передаётся по одной странице за вызов — около 12 мс на 100 кГц. Между страницами снова обслуживаются UART и датчик. Поэтому длинная передача OLED не занимает шину целиком на весь кадр. Расписание основано на `HAL_GetTick()` и работает при переполнении счётчика.

Если датчик или дисплей недоступен, работа UART продолжается, а инициализация повторяется раз в две секунды. Измерения старше 500 мс помечаются недостоверными. Клиент скрывает старые показания при отсутствии телеметрии более секунды и сообщает об обрыве связи после тайм-аутов.

## Калибровка и направление стрелки

1. Установить и применить X=Y=Z=100%. Положить стенд горизонтально вдали от магнита, телефона и корпуса компьютера. Сохранить положение кабелей относительно стенда.
2. На вкладке **«Калибровка»** нажать **«1. Начать сбор»**. Медленно сделать два полных горизонтальных оборота вокруг вертикальной оси за 20–30 секунд. Не наклонять стенд и не перемещать его по столу. Нажать **«2. Завершить обороты»**.
3. Направить верх OLED (сторона с отметкой **0**) на известный магнитный север. Определить его независимым компасом вдали от электроники. Держать стенд неподвижно хотя бы секунду и нажать **«3. Верх OLED направлен на север»**.
4. Из этого положения повернуть стенд на **90° по часовой стрелке, если смотреть сверху**. Верх OLED теперь направлен на восток. Держать секунду и нажать **«4. Поворот на 90° по часовой выполнен»**.
5. Дождаться сообщения **«Калибровка готова»** и сохранения профиля. Проверить четыре положения стенда. Если верх OLED смотрит на север/восток/юг/запад, относительный угол стрелки должен быть примерно 0°/270°/180°/90°.

Окно клиента показывает **тот же угол относительно стенда**, что и OLED. При повороте стенда по часовой стрелке стрелки на обоих экранах должны поворачиваться против часовой. Окно на неподвижном ПК не знает физический поворот монитора и не является отдельным компасом. Неподвижная отметка **0** на OLED обозначает верх экрана, а наконечник стрелки — направление поля.

Сбор выполняет STM32, независимо от частоты обновления GUI. Требуются не менее 100 образцов и покрытие не менее 14 из 16 секторов. На горизонтальную траекторию подгоняется эллипс: его центр убирает постоянное смещение, а положительная симметричная матрица 2×2 исправляет растяжение и перекос XY. Матрица сохраняет площадь эллипса. Шаги 3–4 определяют монтажное смещение угла и направление осей, поэтому подбирать `COMPASS_RIGHT_SIGN` вручную больше не нужно. Резкие изменения внешнего поля, неподвижный датчик, неполный оборот и неправильный угол шага 4 отвергаются. Неподвижность опорных положений проверяется по 12 последним отсчётам. Тайм-аут шага — 3 минуты; насыщение или потеря свежих данных прерывает мастер.

Предыдущий действующий профиль заменяется только после успешного шага 4. **«Отменить»** возвращает его; **«Сбросить калибровку»** удаляет профиль из RAM стенда и файл на ПК. До первой калибровки и во время мастера оба экрана скрывают стрелку, продолжая показывать компоненты поля. Z сохраняет исходную чувствительность: горизонтальные обороты не позволяют определить его смещение. Наклон не компенсируется.

Профили сохраняются в **`calibration_profiles/<UID>.json`** по 96-битному уникальному ID STM32 и модели датчика. Имя COM-порта не используется для выбора профиля. При замене стенда выполнить новую калибровку. Профиль находится в RAM микроконтроллера; после отключения питания он автоматически загружается при следующем подключении клиента. После запуска с питанием и без ПК до загрузки профиля будет `CAL REQUIRED`. Во Flash программа параметры не записывает.

Реализация: `Core/Src/compass_calibration.c` — сбор, эллипс, опорные направления; `Core/Src/magnetometer.c` — чтение и настройка датчика; `Core/Src/compass.c` — применение и UART; `client/calibration_store.py` — сохранение. При инициализации LSM9DS1 выполняются SOFT_RST и очистка аппаратных OFFSET-регистров. У LSM9DS0 параметры магнитометра и аппаратные смещения задаются явно.

Калибровка компенсирует постоянные относительно платы искажения, но не создаёт север в произвольном внешнем поле. Повторять её при изменении окружения, если направление заметно искажается. Магнитное склонение не вводится. Реакция на поднесённый **после калибровки** магнит сохраняется. Один магнитометр измеряет результирующее поле в точке датчика; произвольный ненамагниченный металлический корпус может отклонять стрелку, но не обязан направлять её на свой центр. Основы коррекции описаны в [ST AN3192](https://www.st.com/resource/en/application_note/an3192-using-lsm303dlh-for-a-tilt-compensated-electronic-compass-stmicroelectronics.pdf).

## Масштабные коэффициенты

Коэффициенты имеют шаг 1% и применяются **после калибровки**:

```text
corrected_xy = M × (raw_xy − bias_xy)
B_i = corrected_i × sensitivity × coefficient_i / 100
angle = direction × (atan2(Bx, By) − north_reference), приведённый к 0…360°
```

Без профиля `corrected = raw`, а угол неопределён. Округление поля выполняется до 0.01 мкТл. Одинаковые значения поля и один рассчитанный угол выводятся на OLED и отправляются клиенту. Неравные коэффициенты X/Y намеренно искажают направление; для проверки севера применять 100% по всем осям. Z не участвует в горизонтальном угле. X=Y=0% скрывает стрелку; порог горизонтального поля — 0.50 мкТл. При насыщении направление также скрыто.

Все три коэффициента проверяются до изменения; при ошибке ни один не меняется. После включения питания они равны 100%. Новые значения действуют до следующей команды `SET` или сброса MCU, в том числе при отключённом клиенте. Проценты не изменяют сохранённую калибровку.

## Протокол UART, версия 2

Кадр ASCII:

```text
$<body>*<CRC16, четыре шестнадцатеричных цифры>\n
```

CRC-16/CCITT-FALSE: полином `0x1021`, начальное значение `0xFFFF`, без отражения и финального XOR. Считается по ASCII-байтам `body`, без `$`, `*` и перевода строки. Проверочный вектор: `123456789 → 29B1`. Тело не длиннее 160 байт. Приём допускает LF и CRLF; отправка использует LF. Новый `$` начинает новый кадр и позволяет восстановиться после повреждения потока.

| Тело запроса | Тело ответа |
| --- | --- |
| `seq,PING` | `seq,PONG,2,model,address,uid` |
| `seq,GET` | `seq,OK,GET,kx,ky,kz` |
| `seq,SET,kx,ky,kz` | `seq,OK,SET,kx,ky,kz` |
| `seq,CAL,GET` | `seq,OK,CAL,state,samples,coverage,ready` |
| `seq,CAL,START` / `FINISH` / `NORTH` / `TURN` / `CANCEL` / `RESET` | `seq,OK,CAL,state,samples,coverage,ready` |
| `seq,CAL,READ` | `seq,OK,CALDATA,bx,by,m00,m01,m11,north,direction` |
| `seq,CAL,LOAD,bx,by,m00,m01,m11,north,direction` | `seq,OK,CAL,state,samples,coverage,ready` |
| Некорректная команда | `seq,ERR,reason` |

`seq` — целое число 1…65535. Ответ повторяет номер запроса. `address` в PONG передаётся десятичным числом, например 29 означает `0x1D`. При отсутствии датчика PONG всё равно подтверждает работу микроконтроллера, модель — `NONE`, адрес — 0. Наличие свежего измерения определяется по флагам DATA.

`uid` — 24 шестнадцатеричных символа. `state`: 0 — без профиля, 1 — сбор, 2 — ожидание севера, 3 — ожидание поворота, 4 — готово. `samples` — число собранных точек; `coverage` — число секторов из 16 после попытки подгонки; `ready` — наличие ранее завершённого профиля. Статус также передаётся каждые 200 мс как `0,CALSTAT,state,samples,coverage,ready`. В `CALDATA`/`LOAD`: `bx,by` — смещения в тысячных долях отсчёта датчика; `m00,m01,m11` — матрица, умноженная на 1000000; `north` — сотые градуса; `direction` — ±1. Загрузка проверяется до изменения профиля. Повторы шагов в уже достигнутом состоянии не повторяют сбор/опорное измерение.

При неверном CRC/формате нельзя доверять номеру запроса, поэтому ответ — `0,ERR,BAD_FRAME`. Другие причины: `BAD_REQUEST`, `BAD_COMMAND`, `RANGE`, `FRAME_TOO_LONG`, `RX_OVERFLOW`, `UART_ERROR`.

Телеметрия отправляется автоматически, номер 0 зарезервирован для сообщений стенда:

```text
0,DATA,tick_ms,bx,by,bz,angle,kx,ky,kz,flags
```

`bx`, `by`, `bz` — знаковые целые в единицах 0.01 мкТл; `angle` — сотые градуса, либо −1 при неопределённом направлении. `tick_ms` — 32-битное время работы STM32 в миллисекундах. `kx`, `ky`, `kz` — действующие проценты. `flags` — битовая маска:

| Бит | Значение |
| --- | --- |
| 0 (`1`) | Есть свежее измерение |
| 1 (`2`) | Направление определено |
| 2 (`4`) | Датчик близок к насыщению |
| 3 (`8`) | OLED инициализирован, передача кадров не завершилась ошибкой |
| 4 (`16`) | Есть завершённый профиль калибровки |
| 5 (`32`) | Выполняется калибровка; угол скрыт |

В штатном режиме после калибровки флаги равны **27** (1+2+8+16). До калибровки при исправных устройствах — **9** (1+8), угол −1.

Клиент держит один неподтверждённый запрос, ждёт до секунды и делает до трёх отправок с тем же номером. `SET` задаёт абсолютные значения и безопасен при повторе. Во время ожидания ответов телеметрия продолжает приниматься. Периодический PING проверяет связь.

## Проверки без стенда

```sh
python3 -m unittest discover -s tests -v
python3 tools/build_firmware.py
```

Тесты используют настоящий C-код прошивки с заменой HAL на модель I²C/UART и Python-клиент. Проверяются идентификация обоих датчиков, сброс OLED с сохранением остальных битов PCA9538, передача страниц, знаки/единицы поля, квадранты угла, нулевой вектор, пределы коэффициентов, атомарное отклонение команды, CRC, фрагментация, переполнение UART, восстановление приёма и журнал обмена. Проверки калибровки моделируют смещение, наклонённый эллипс, неравномерную скорость вращения и оба направления осей: после коррекции ошибка на этих искусственных данных менее 0.35°. Это не оценка аппаратной точности. Дополнительно проверены отказ при неполном обороте, отмена с сохранением старого профиля, обмен профилем, его загрузка при новом подключении и сброс на ПК/стенде.

Программные проверки не заменяют проверку на плате: после мастера проверить четыре положения, совпадение OLED/GUI и реакцию на магнит.
